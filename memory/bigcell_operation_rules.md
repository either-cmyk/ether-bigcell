## 1. 시간 목표: 사업자당 15분 이내

**Why**: 매일 반복 루틴이라 시간이 길어지면 누적 피로도 큼. 하루 5개 사업자 → 사업자당 15분 상한.

**How to apply**:
- 기존 탭의 gviz 타임아웃 피하려면 새 탭에서 시작
- 불필요한 확인 스크린샷 최소화
- 각 단계 완료 즉시 다음 단계로
- 예상 타임라인: 다운로드/파싱 3분 → doPost 2분 → 열 삽입 3분 → 수식 채우기 4분 → 값 변환 2분 → 검증 1분

## 2. 대상 날짜: KST 기준 전날 하루치만

기본 대상 = "서울(KST) 기준 현재일 - 1일" 하루치만 처리. 예: KST 4/24 실행 → 4/23만 갱신.

**Why**: 매일 돌리는 루틴의 표준. 시트 중간에 빠진 날짜(예: 클린인테크 4/7~9, 마인플로 4/10~20)가 보여도 사용자가 명시 요청 없으면 채우지 말 것. 과거 누락일을 임의로 채우면 발주/재고 계산과 어긋남.

**How to apply**:
- 날짜는 항상 KST 기준 어제로 고정 (`date -d "yesterday" +"%Y. %-m. %-d"` 또는 JS에서 `new Date(Date.now()-86400000)`)
- 마지막 행+1부터 append (덮어쓰기 금지, 같은 날짜 재갱신이 필요한 경우만 예외)
- 중간 빠진 날짜는 사용자에게 먼저 안내 후 대기

## 3. 검증은 상단 행이 아니라 전체 비영값 개수로

**Why**: 판매량 0인 상품은 빅셀 데이터에 아예 안 나오므로, 그로스 재고 DB에서 매칭 안 되는 상품은 정상적으로 0 표시. 상단 행이 전부 0이어도 전체적으로는 정상일 수 있음. 2026-04-08에 상단 행만 보고 타입 문제로 오판하여 불필요한 진단에 시간 낭비한 사례.

**How to apply**:
- 새 날짜 컬럼 입력 후 검증: gviz `COUNT(XX) WHERE XX <> 0`으로 비영값 개수 확인
- Standalone API 응답의 `newNonZero` vs `oldNonZero` 비교 → 비슷한 수준이면 정상 (±5 범위)
- 비영값이 **0개**인 경우에만 타입 불일치 등 문제를 의심

## 4. 금지 동작

- **Ctrl+Z 절대 금지**: UI 실수 후 되돌리기로 완료 작업 날아가는 사고 반복. 잘못 눌렀으면 Escape + 상태 재확인
- **Ctrl+H 찾기/바꾸기 전체 시트 금지**: 30,034셀 터치 전례로 불신 (2026-04-23 사태)
- **스크린샷 확대 해석 의존 금지**: gviz COUNT 쿼리로 숫자 검증
